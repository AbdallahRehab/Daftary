## Decisions

| # | Topic | Choice | Why |
|---|---|---|---|
| 1 | Overlay mechanism (S3 not run as a spike) | Primary: `androidComponents.onVariants { variant.sources.manifests.addStaticManifestFile("sms_capability/AndroidManifest.xml") }` when the switch is on. The overlay is `android/app/sms_capability/AndroidManifest.xml`, with READ_SMS only. The fallback module was not needed. | It was observed to work (see S3, "Observed during T104/T105"). No module, and no hard-coded compileSdk. |
| 2 | Switch reading | `providers.environmentVariable("DAFTARY_SMS_IMPORT") == "true"` OR `providers.gradleProperty("daftary.smsImport") == "true"`. Only the literal `true` enables it. | CHK013. Provider-based reads are configuration-cache safe. Default off. |
| 3 | Locating the merged manifest | The script `find`s `process<Variant>MainManifest/AndroidManifest.xml` under `build/app/intermediates/merged_manifest/<variant>/`. If it is not found, the script fails. | AGP 8.11 also writes `output<Variant>AppLinkSettings/AndroidManifest.xml` there, so a plain `find` would be ambiguous. |
| 4 | Script expectation source | Follows `DAFTARY_SMS_IMPORT`. `--expect-read-sms` / `--expect-no-read-sms` override it for `-P` builds. The variant defaults to `release`. | One script for CI, local use and both switch forms. |
| 5 | "No receiver or service declared by the SMS code" | Fails on any `<receiver>`/`<service>` named `com.daftary.*` (or relative `.X`). Library receivers and services are allowed and printed: there are 9 today (flutter_local_notifications, profileinstaller, datatransport, share_plus, ML Kit, gms metadata). It also fails on any SMS_RECEIVED, SMS_DELIVER, WAP_PUSH_DELIVER or WAP_PUSH_RECEIVED action, and on an ACTION_SEND filter on any component other than ShareTargetActivity, so never on MainActivity. | A fixed allow-list of library components would break on every dependency bump without adding SMS safety. The SMS-action check catches a library that tries to receive SMS. `RECEIVE_MMS`, `RECEIVE_WAP_PUSH` and `WRITE_SMS` are also asserted absent. That is stricter than T105 and matches the manifest's removal markers. |
| 6 | CI job `android-manifest` | An additive new job. It runs `flutter build apk --release --config-only` (writes the gitignored `gradlew` and `local.properties`), then `./gradlew :app:processReleaseMainManifest` plus the script, once unset and once with `DAFTARY_SMS_IMPORT=true`. | It does not compile the app, so it is fast. The release variant is what ships. The existing `test` job is unchanged. **Not run on GitHub.** Its commands were run locally. |
| 7 | Release workflow (T124) | `DAFTARY_SMS_IMPORT: "true"` is set only on the "Build APK" step. A new "Verify APK permissions" step runs on every `dist/*.apk` (universal and arm64). It uses `aapt dump permissions`: READ_SMS must be present and RECEIVE_SMS, SEND_SMS, READ_PHONE_STATE, RECEIVE_MMS, RECEIVE_WAP_PUSH and WRITE_SMS absent. It then uses `aapt dump xmltree`: the owner of every `android.intent.action.SEND` must be exactly ShareTargetActivity. `aapt` comes from the newest `$ANDROID_HOME/build-tools`. The signing and keystore steps are untouched. | Additive. **Owner gate:** pushing a tag now ships a READ_SMS APK. OQ5 (Play Protect in Egypt) is still open, so the owner must decide before the next tag (spike S4 fallback: two APKs, or revert this env line). |
| 8 | Permission APIs in Kotlin | Platform APIs (`checkSelfPermission`, `Activity.requestPermissions`, `shouldShowRequestPermissionRationale`, minSdk 24) instead of `ActivityCompat`/`ContextCompat`. | They behave the same on API 23+, and they avoid relying on androidx-core being on the app's compile classpath. `0x5A11` is below 16 bits, so `FlutterFragmentActivity` forwards the result to the plugin's `RequestPermissionsResultListener`. |
| 9 | `dialogShown` | `Application.ActivityLifecycleCallbacks.onActivityPaused` for the requesting activity, registered for the duration of the request only. | The binding's lifecycle needs `flutter_plugin_android_lifecycle`, and adding a dependency is not allowed. Application callbacks exist on every API level. |
| 10 | Already granted on `requestPermission` | It replies at once with `dialogShown: false` and starts no system activity. | `EnableSmsImport` already avoids this path, so this is defensive. |
| 11 | Pending request across activity lifecycle | It survives a configuration change: the listener is re-added on reattach. It fails with `no_activity` on a final detach or an engine detach. A second call while one is pending gets `request_in_progress`. | Contract §2.3. An empty `grantResults` (interrupted) falls back to the live `checkSelfPermission`. |
| 12 | Inbox selection (S2 not run) | Rung 0: `UPPER(address) IN (?,…) AND (date > ? OR (date = ? AND _id > ?))`. On the first page (`afterId == null`) it is `… AND date > ?`. Every value is a bind argument. Projection `_id, address, date, body`. Sort `date ASC, _id ASC`. No SQL LIMIT. No runtime fallback to a looser query: a provider failure is `query_failed`. | Contract §2.4 and S2 default. The first-page form matches `FakeSmsInboxGateway` (strictly after `afterDate` when there is no id), which `RunInboxScan` was tested against. |
| 13 | Page size vs skipped rows | It reads until `limit` rows **with a body** are collected or the cursor ends. Rows with a null body or address (MMS) are skipped and don't count. | If skipped rows counted, a page could come back short and Dart would wrongly treat the inbox as finished. |
| 14 | Truncation | 4,000 characters, and it never splits a surrogate pair. `truncated: true` is set. | FR-098. A lone surrogate would be mangled by the codec. |
| 15 | Kotlin argument rules | It rejects (`invalid_args`, never clamps) the following: an empty sender list or one over 200; a sender that is empty, over 32 characters, not upper-case or contains whitespace; a negative `afterDate` or `afterId`; and a `limit` outside 1..200. Numbers are accepted as Int or Long. The same rules are repeated in `PlatformSmsInboxGateway` before any call. | Contract §2.4 and §6. In Dart a violation is `SmsInboxQueryFailure`. **I did not add a debug `assert`** (the contract mentions one), because the contract's own tests require "limit 201 rejected before the call" as a returned failure, and an assert would throw instead. |
| 16 | Install source | API 33+ uses `packageSource`: STORE → store; DOWNLOADED_FILE, LOCAL_FILE or OTHER → notStore; UNSPECIFIED falls through. API 30+ checks `installingPackageName` against Play, Samsung, Huawei and Xiaomi: in the list → store, another installer → notStore, null → unknown. Below API 30, or on any exception → unknown. `getCapabilities.isStoreInstall` now reports it (store → true, notStore → false, unknown → null). | Contract §2.3 and S4. Dart doesn't read `isStoreInstall` yet, so this is harmless. |
| 17 | Threading | One `Executors.newSingleThreadExecutor()` per engine attach. Replies are posted through `Handler(mainLooper)`. `shutdownNow()` on engine detach, and the read loop checks the interrupt flag. The cursor is closed by `use {}`. | Contract §5. |
| 18 | **`previouslyRequested` (the known T107 issue)** | **Port change:** `SmsPermissionService.request({required bool previouslyRequested})`. `RequestSmsPermission` now does: capability check, then `getSettings()` (a failed read stops before the dialog), remember `permissionRequested`, then `markPermissionRequested()` (unchanged, still before the dialog), then `request(previouslyRequested: <value read>)` inside the runner. | It is explicit, and it keeps the "persist before the dialog" contract. The adapter stays pure: it needs no settings read, and has no race with the write. A first request is never classified `permanentlyDenied`. Tested: `[false, true]` over two calls, and `true` when the flag was already stored. |
| 19 | `getStatus()` inputs | The adapter reads the settings repository (injected): `previouslyRequested` = stored `permissionRequested`, and `previouslyGranted` = stored `isEnabled`. The import is only enabled after a grant, so "enabled but not granted" means revoked (FR-070). It passes `dialogShown: true` and `sdkInt: 0`, so restricted settings are **never** inferred from a status check, only from a request result. If the settings can't be read, both are false (→ `denied`). | No persisted "ever granted" flag exists, and none was added (no schema change). Known limitation: after a sideloaded Android 15 restricted block, a later status check reads `permanentlyDenied`, not `restrictedBlocked`. Both lead the UI to App info. |
| 20 | `getStatus` takes no parameters | I left `getStatus()` parameterless. Only `request` changed. | Adding parameters would touch `GetSmsPermissionStatus`, `EnableSmsImport` and `RunInboxScan` and their tests. `getStatus` has no ordering problem, because nothing writes the flags during a status check. |
| 21 | `app_settings` | It is already a dependency (`pubspec.yaml`: `app_settings: ^9.0.0`). Imported `as app_settings`. `openAppInfo` calls `AppSettings.openAppSettings()` with the default type `settings`, which is App details on Android. A test confirms the channel receives `openSettings` with `type: settings`. The opener is injectable for tests. A failure becomes `UnknownFailure('sms_app_info_unavailable')`, a fixed token. | Contract §2.7. No native `openAppInfo` method was added. I added no new failure class, so the domain entity file is untouched. |
| 22 | Short-circuits | Both adapters read `readSmsDeclared` through `getCapabilities`, cached once it succeeds because the manifest can't change in-process. A failed reply is treated as not declared, isn't cached, and stays `isAndroid: true` so shares keep working. When the capability is off: `queryInbox` → `SmsCapabilityUnavailableFailure`; `getStatus` and `request` → `Right(unavailable)`; `openAppInfo` → `Right(unit)` without opening. No inbox or permission method is called. A channel `unavailable` code from the permission methods maps to `Right(unavailable)` as well. | Invariant 5, and the same behaviour as `UnavailableSmsPermissionService`. |
| 23 | Single flight | `PlatformSmsPermissionService.request` shares one in-flight future between concurrent callers and releases it on completion. | Contract §3 (`request_in_progress` should not surface). |
| 24 | Module | `smsInboxGateway(SmsChannelClient)` and `smsPermissionService(SmsChannelClient, SmsInboxGateway, SmsImportSettingsRepository)` select the `Platform*` adapters on `Platform.isAndroid`, and `Unavailable*` elsewhere (and under `flutter test`). | T107. Getter → method because of the new dependencies, which forced codegen. |
