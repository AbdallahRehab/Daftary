# Phase 0 Research: Home Dashboard

The spec (012) carries zero `NEEDS CLARIFICATION` markers — the one open product question flagged by ROADMAP-PLAN.md (whether Home replaces People as tab 1) was resolved with a documented default in spec.md's Assumptions. This document resolves the remaining *technical/design* decisions needed to start Phase 1 design, reusing precedents already established by spec 001 (`people`/`transactions`) and spec 007 (`finance`) wherever they apply, per the constitution's Refactoring Discipline.

## 1. Where `GetDashboardSnapshot` and the relocated Overview screen live

**Decision**: A new feature module, `lib/features/dashboard/`, owns the coordination use case (`GetDashboardSnapshot`) and the entire presentation layer for the home screen (`DashboardCubit`/`DashboardState`/`HomePage`, plus the relocated `OverviewSummaryCard` and new widgets). `GetOverview`, `OverviewSummary`, `PersonSummary`, and `TransactionsRepository` all stay exactly where they are in `transactions/domain/` — only the *presentation* that renders `GetOverview`'s output moves.

**Rationale**: `GetDashboardSnapshot` composes two use cases from two different existing features (`transactions`' `GetOverview` and `finance`'s `GetFinanceSummary`/`GetFinanceHistory`). Placing it inside `transactions/domain/` would give the `transactions` feature a dependency on `finance` for no reason intrinsic to balance-tracking; placing it inside `finance/domain/` would do the reverse. Per constitution Principle II ("Feature-First Modularity") and V ("Domain-Driven Business Logic... multi-repository coordination... justifies [a use case's] existence"), a coordinator that genuinely spans two features belongs in a third feature that depends on both, one-directionally (`dashboard → transactions`, `dashboard → finance`), never the other way. This mirrors 007's own precedent of keeping `finance` structurally separate from `transactions` specifically to avoid an unjustified merge (007 `research.md` Decision 1). Moving the presentation layer alongside it (rather than leaving `HomePage` in `transactions/presentation/` while its Cubit lives in `dashboard/`) keeps each feature's presentation/domain/data triad self-contained, matching every other feature in this codebase.

**Alternatives considered**: Keep `OverviewPage`/`OverviewCubit` in `transactions/presentation/` and only add `GetDashboardSnapshot` to a domain-only `dashboard` folder — rejected: it would leave the screen's Cubit physically separated from its own use case's feature folder, and `transactions/presentation/` would still end up importing `finance` entities to render the finance-snapshot half of the screen, which is the exact coupling the folder split was trying to avoid in the first place. Add `GetDashboardSnapshot` directly to `finance/domain/` (since `finance` was built more recently and roadmap section 12 ties Insights conceptually to spending data) — rejected for the same reason, just mirrored: no basis for `finance` owning `transactions`' balance-coordination logic either. A generic `home/` naming instead of `dashboard/` — rejected as a purely cosmetic naming choice with no material difference; `dashboard` matches the terminology already used throughout ROADMAP-PLAN.md §V1.5.2 and `docs/project.txt` §12.

## 2. Modeling the partial-error (one aggregate fails, one succeeds) state

**Decision**: `DashboardState` carries two fully independent sub-statuses — `overviewStatus`/`financeStatus`, each a `LoadStatus` enum (`loading`/`success`/`failure`) — alongside their own nullable data (`overviewSummary`/`financeSummary`) and nullable error messages. No single combined "status" field collapses the two. Derived getters (`isFullyLoading`, `isFullFailure`, `isCombinedEmpty`) are computed from the pair, never stored redundantly.

**Rationale**: Directly implements FR-002/FR-003/FR-004 — a failure in one aggregate must never hide or block the other, and each must be independently retryable. Two independent enum fields (rather than one `DashboardStatus.partialError` catch-all) let the UI render each card's own state directly from its own fields with zero re-derivation ambiguity about *which* side failed, and let `DashboardCubit.retryOverview()`/`retryFinance()` update exactly one field via `copyWith()` without touching the other — consistent with constitution Principle IV (immutable state, minimal re-emission).

**Alternatives considered**: A single `DashboardStatus` enum with a `partialError` variant plus a `failedSide` marker — rejected, forces every state-reading widget to branch on an extra enum just to reconstruct what two independent booleans already express directly, and makes "both failed" vs. "one failed" a derived special case instead of the natural result of checking two fields. Two separate Cubits (one per aggregate) composed at the widget layer — rejected: the screen's combined-empty-state and "both failed" full-screen error state need to reason about both aggregates together, which is exactly the kind of cross-aggregate coordination a single Cubit (backed by the single `GetDashboardSnapshot` use case) is meant to own; splitting into two Cubits would just move the coordination problem into the widget tree, which constitution's Widget/Build Discipline explicitly discourages (side effects/coordination belong in BLoC, not build methods).

## 3. Detecting the combined first-run empty state (FR-005)

**Decision**: `GetDashboardSnapshot` determines "zero people AND zero finance entries" from data the existing use cases already return or can cheaply provide, adding no new SQL query:
- **Zero people**: `OverviewSummary.peopleTheyOweYou.length + OverviewSummary.peopleYouOweThem.length + OverviewSummary.settledCount == 0` — `GetOverview`'s docstring already establishes it counts "all people, active and archived," so this sum is a true zero-people check, not merely "zero non-zero balances" (which `isAllSettled` alone would give).
- **Zero finance entries**: a call to the existing `FinanceRepository.getHistory(limit: 1)` (from 007's contract) with no filter, checking whether it returns zero rows. This is deliberately *not* "this month's `FinanceSummary` totals are zero" — a user could have entries only in a prior month, which must not be reported as "no finance entries at all" (spec Edge Cases explicitly distinguishes these).

**Rationale**: FR-005 requires true, permanent zero-activity detection, not merely a same-period-summary check, and the constitution's Financial Domain Override (never let a screen imply "nothing has ever happened" when something has) makes getting this distinction right worth the one extra, already-existing, cheap (`limit: 1`) call. Both signals reuse use cases 007 and `transactions` already expose — no new repository method, no new SQL, satisfying FR-016 ("MUST NOT alter the underlying calculation logic... of the existing... sources").

**Alternatives considered**: Treating "this month's `FinanceSummary` is all zero" as sufficient for the finance half of the combined empty state — rejected per the Edge Cases scenario above; it would incorrectly show the encouraging first-run message to a user who already has months of history, which is a worse and more confusing experience than showing their (correctly empty-for-this-month) snapshot normally. Adding a new `hasAnyPeople`/`hasAnyFinanceEntries` repository method to each feature — rejected as an unjustified new surface when the existing `getHistory(limit: 1)` and `GetOverview`'s already-returned counts answer the same question for free.

## 4. Feature-flag mechanism for the hidden Add Occasion / Scan Paper quick-action slots

**Decision**: A minimal `lib/core/config/feature_flags.dart` with two `const bool` values (e.g. `kOccasionsFeatureEnabled = false`, `kOcrScanFeatureEnabled = false`), read by `QuickActionRow` to decide whether to render or hide each future slot. No remote config, no persisted setting, no runtime toggle UI.

**Rationale**: The app is fully offline by design (constitution: no network dependency introduced without explicit justification, and none exists here) — a remote-config or backend-driven flag system would be pure speculative infrastructure for a need that doesn't yet exist. A compile-time `const bool` is the simplest mechanism that satisfies FR-008 today and gives the *future* Occasions/OCR features (per ROADMAP-PLAN.md §V2.1/§V2.4) a single, obvious place to flip one line to `true` when they ship — no code in `dashboard/` needs to change at that point, only the flag's value. Placing it in `core/config/` (not inside `dashboard/`) is justified per Principle II specifically because two *separate, future* features (Occasions, OCR) — not just this one — are the ones expected to eventually write to it; that is a real, if forward-looking, cross-feature concern, not a premature abstraction for a hypothetical.

**Alternatives considered**: A `FeatureFlags` value tucked inside `dashboard/domain/` — rejected, since the flags conceptually belong to the *features being gated* (Occasions, OCR), not to the screen that happens to read them first; keeping them in `core/config/` avoids `dashboard/` looking like it owns a decision about unrelated future features. An enum-keyed map (`Map<Feature, bool>`) instead of two named constants — rejected as needless indirection for exactly two flags; a named `const bool` per flag is simpler to read, grep, and flip.

## 5. Router and bottom-navigation changes

**Decision**: `app_router.dart`'s existing `GoRoute(path: '/overview', ...)` keeps its path string unchanged; only its `builder` is swapped from `OverviewPage` to the new `HomePage`. `main_shell.dart`'s corresponding `NavigationDestination` label swaps from `l10n.overviewTitle` to a new `l10n.homeTitle` key; the destination's position (index 1, after People) and icon are otherwise unchanged. People remains tab index 0 / the default landing route (spec Assumption).

**Rationale**: Directly implements the spec's "in-place extension, not a new route" framing and FR-014's localization requirement for the new label. Keeping the path string `/overview` (rather than renaming it to `/home`) avoids touching every other place in the codebase that might reference that path (none currently do outside `app_router.dart`/`main_shell.dart` per a full-repo search, but keeping the string stable is strictly lower-risk than renaming it for a purely cosmetic reason) and matches research.md Decision 9 from 007, which already anticipated Home Dashboard as "the right place to make a holistic navigation-architecture decision once more of the roadmap's shape is known" — this feature deliberately does *not* attempt that holistic reshuffle (see spec Assumptions), only the minimal relabel the roadmap itself scoped to this feature.

**Alternatives considered**: Renaming the route to `/home` — rejected as an unnecessary, purely cosmetic churn with no functional benefit and a larger (if still small) diff surface for zero user-facing gain (users never see the path string). Promoting Home to tab index 0 now — rejected per spec Assumptions; explicitly deferred to a future, deliberate IA decision once Occasions exists (ROADMAP-PLAN.md §9).

## 6. Testing approach specifics

**Decision**: Same three-tier approach as 007/001 — use-case unit tests with faked use case dependencies (not faked repositories, since `GetDashboardSnapshot` depends on other use cases, not repositories directly), `DashboardCubit` tests with `bloc_test`/`mocktail`, widget tests for `HomePage`, and one `integration_test/dashboard_flows_test.dart`. The partial-error and combined-empty-state paths (Decisions 2-3) get dedicated Cubit-level tests since they are this feature's highest-risk, easiest-to-regress behaviors — and SC-004 (zero fabricated Insights/Upcoming content) gets its own explicit assertion that only the two approved placeholder strings can ever render in those two sections.

**Rationale**: Constitution Principle XVI; consistency with the established testing shape avoids introducing a second testing convention for no reason. The SC-004 test in particular is the direct, permanent regression guard against someone later "helpfully" adding a hardcoded fake insight to make the screen look more finished before the AI Assistant actually exists.

**Alternatives considered**: None — this is a direct precedent reuse, not an open design question.
