# Phase 0 Research: Reports & Data/Privacy Controls

The spec (013) carries zero `NEEDS CLARIFICATION` markers — the two open implementation questions it flagged (export file format, default trend window) are resolved below, along with every other technical decision needed to start Phase 1 design. Precedents from spec 001 (`people`/`transactions`), spec 007 (`finance`), and spec 012 (`dashboard`'s cross-feature-module justification) are reused wherever they apply, per the constitution's Refactoring Discipline.

## 1. Feature module split: Reports stays in `finance`, Export/Delete get a new `data_privacy` feature

**Decision**: Reports (`ReportsPage`/`ReportsCubit`/`GetSpendingTrend`) is added inside the existing `lib/features/finance/` module from spec 007. Export and Delete get one new module, `lib/features/data_privacy/`.

**Rationale**: Reports is finance data through and through — a monthly income/expense trend and a category breakdown are just 007's own `GetSummary`/`GetCategoryBreakdown` called across a range, with no dependency on `people`, `transactions`, or `settings`. Per constitution Principle II, code that is genuinely owned by one feature stays there rather than being pulled into a new module for no reason. Export and Delete are the opposite case: both touch `People`, `MoneyTransactions`, `FinanceEntries`/`FinanceCategories`, and `AppSettings` equally — no single existing feature should own "export everything" or "delete everything," for the same reason spec 012 gave for creating `dashboard` as a new module rather than bolting `GetDashboardSnapshot` onto `transactions` or `finance`.

**Alternatives considered**: Putting Export/Delete inside `settings` (since "Delete My Data" is reached from `SettingsPage`) — rejected: `SettingsPage` is only the *entry point* for Delete, not its owner; folding a cross-cutting, multi-repository capability into the `settings` feature would give `settings` an inappropriate dependency on `people`/`transactions`/`finance`, the same anti-pattern spec 012's research.md Decision 1 already rejected for the symmetric case. A combined `reports_data_privacy` module for both halves — rejected: Reports and Export/Delete have no functional relationship to each other beyond being planned in the same roadmap slot for scheduling convenience (ROADMAP-PLAN.md §V1.5.3's own words: "bundled... because both are low-risk... not because they're related"); forcing them into one folder would misrepresent that as an architectural relationship.

## 2. Composing the export without adding new repository methods

**Decision**: `ExportUserData` sources every entity from methods that already exist today (verified against the actual repository interfaces in `lib/features/people/domain/repositories/people_repository.dart`, `lib/features/transactions/domain/repositories/transactions_repository.dart`, and 007's `contracts/finance_repository.md`/`contracts/category_repository.md`):

- **People**: `PeopleRepository.searchActivePeople()` + `searchArchivedPeople()` (both with no filter), concatenated — covers every person, active and archived, with zero new methods.
- **Transactions**: for each person from the step above, `TransactionsRepository.getPersonHistory(personId)`, flattened. This covers every non-deleted transaction in the app, because a person can never be *deleted* (as opposed to archived) while they still have any transaction — `PeopleRepository.deletePerson` already enforces this via `PersonHasTransactionsFailure` — so every transaction is provably reachable through some still-existing person.
- **Finance entries**: `FinanceRepository.getHistory(filter: null, limit: N, offset: 0)`, paged with a generous page size (e.g. 500) and repeated with increasing `offset` until a page returns fewer rows than requested — the same existing, unfiltered, paginated method 007 already exposes, just called to completion rather than once.
- **Categories**: `CategoryRepository.getCategories(type: income, includeArchived: true)` + `getCategories(type: expense, includeArchived: true)`.
- **Settings**: `SettingsRepository.getLanguagePreference()` + `getThemeModePreference()`.

**Rationale**: Every one of these calls already exists for a reason unrelated to export (search, history, breakdown, preferences) — composing them is exactly the "reuse existing use cases/repositories wherever the data already exists" principle ROADMAP-PLAN.md §6 states as the concrete, per-feature answer to avoiding duplicated sources of truth, applied here for the first time to a feature whose entire job is reading *across* every other feature. Zero new abstract methods means zero new surface for `people`/`transactions`/`finance`'s existing, already-tested repositories to get wrong.

**Alternatives considered**: A new `getAllPeople()`/`getAllTransactions()`/`getAllFinanceEntries()` convenience method on each repository — rejected as unjustified new surface (constitution: "avoid unjustified abstractions") when the composition above achieves the identical result using methods that already exist and are already tested. A raw SQL dump bypassing the repository layer entirely — rejected outright: it would violate Principle VI (Presentation/Domain never touch the DB directly) and Principle I (Data owns all DB access behind a repository), and would silently exclude any future soft-delete/filtering logic a repository method might apply.

## 3. Export scope: active (non-deleted) records only

**Decision**: The export includes only currently-active data exactly as each existing method already returns it — active and archived people (not deleted, since deletion is disallowed while referenced), non-deleted transactions (`getPersonHistory` already excludes soft-deleted rows), non-deleted finance entries (`getHistory` already excludes soft-deleted rows), active and archived categories. Soft-deleted rows still inside their undo window, or already permanently soft-deleted, are not included.

**Rationale**: This is simply "whatever the existing methods already return" with zero additional filtering logic — the simplest, most consistent choice, and it matches what the user actually sees as "their data" anywhere else in the app. Including soft-deleted rows would require new repository methods explicitly reaching past the soft-delete boundary, which Decision 2 already ruled out as unjustified new surface.

**Alternatives considered**: Including soft-deleted rows for completeness/audit purposes — rejected: no existing screen in the app shows a user their own soft-deleted records, so an export that did would show the user MORE than the app itself does anywhere else, which is a confusing inconsistency rather than a genuine benefit, and it would require new repository surface (Decision 2).

## 4. Export file format: a single, section-delimited CSV file

**Decision**: One `.csv` file (per ROADMAP-PLAN.md §11's own "CSV serialization" framing for `ExportUserData`), structured as consecutive labeled sections — a `## PEOPLE` marker line, a header row, then that entity's data rows, a blank line, then `## TRANSACTIONS`, and so on for Transactions, Finance Entries, Categories, and Settings.

**Rationale**: FR-007/FR-008 require "a single export file"; CSV is a genuinely non-proprietary, universally-readable format any user can open in a text editor or spreadsheet tool without this app (spec Assumptions' "widely-readable, non-proprietary" criterion), and it needs no new dependency beyond simple string-building (Dart's standard library is sufficient — no CSV-writing package is even required, given the data shapes involved are simple and fully controlled by this feature). Section markers keep genuinely heterogeneous entities (different column sets) inside one literal file without inventing a nested format.

**Alternatives considered**: A ZIP archive containing one real `.csv` per entity — rejected: each individual CSV would import into a spreadsheet tool slightly more cleanly, but it requires a second new package dependency (an archive/zip library) for marginal benefit at this app's realistic single-user data scale, when `share_plus` is already the one dependency this feature needs to justify. A single JSON file — rejected in favor of honoring ROADMAP-PLAN.md §11's explicit "CSV serialization" call-out for this exact use case, and because CSV's row/column shape maps more directly onto how a non-technical user (this product's explicit target, `docs/project.txt` §38) would recognize and use "their data in a spreadsheet."

## 5. `DeleteAllUserData` atomicity

**Decision**: A new `Future<void> deleteAllUserData()` extension method on `AppDatabase`, in `lib/core/database/data_wipe.dart`, wraps a bulk `DELETE FROM` of every table (`People`, `MoneyTransactions`, `TransactionAuditEntries`, `FinanceEntries`, `FinanceCategories`, `AppSettings`, `OnboardingStatus`) inside a single `db.transaction(() async { ... })` block — `drift`'s transaction API automatically rolls back every statement if any one of them throws, giving true all-or-nothing atomicity without hand-rolled compensation logic. A new `DataWipeRepository` (Domain, one method) and `DataWipeRepositoryImpl` (Data) wrap this exactly like every other repository wraps its DAO, per Principle VI.

**Rationale**: Directly implements FR-018 (never a partial deletion) using `drift`'s own built-in transaction primitive — the same mechanism `transactions_repository_impl.dart` already uses internally when writing a `MoneyTransaction` + its `TransactionAuditEntry` together, so this is a proven, already-used pattern in this codebase, not a new technique. Placing the extension in `core/database/` (not inside `data_privacy/data/`) mirrors `balance_queries.dart`'s existing precedent exactly: a capability that must reach every table across every feature belongs at the `core/database/` boundary, not inside any one feature's DAO, because a DAO importing every other feature's tables would invert the dependency direction Principle I requires.

**Alternatives considered**: Calling each feature's own repository-level delete method in a loop (e.g., delete every person, every category) — rejected: existing delete methods enforce business rules (e.g., `deletePerson` refuses a person with transactions) that are exactly wrong for a full wipe, and looping N deletes has no shared transaction boundary across features' separate DAOs, reintroducing the partial-failure risk FR-018 prohibits. A soft "mark everything deleted" flag instead of a hard row wipe — rejected: FR-017 requires the app to behave exactly like a fresh install afterward, which a soft-delete flag would not achieve (every screen would still need to filter it out, and the constitution's data-minimization spirit favors actually removing data the user explicitly asked to be gone).

## 6. Returning to onboarding after a successful deletion

**Decision**: After `deleteAllUserData()` commits, `DeleteAllUserData` (the use case) returns success; `DeleteAccountCubit` then calls the existing, already-re-callable `OnboardingCubit.initialize()` (root-scoped `@lazySingleton`, per `lib/features/onboarding/presentation/cubit/onboarding_cubit.dart` — it is a plain async re-resolution, not a one-shot startup-only call) and triggers a navigation (`context.go('/')`). Because every table is now empty, `ResolveOnboardingStatus`'s existing logic (`OnboardingStatus.isComplete` is gone, and `hasAnyPerson()`/`hasAnyTransaction()` both now return `false`) naturally resolves to `showOnboarding`, and `app_router.dart`'s existing `redirect:` callback (already checking `OnboardingCubit`'s state on every navigation) sends the app to `/onboarding` — with no new onboarding capability, no app restart, and no new redirect logic.

**Rationale**: This is the minimal possible integration — reusing three already-existing, already-tested mechanisms (`ResolveOnboardingStatus`'s existing person/transaction-existence check, `OnboardingCubit.initialize()`'s existing re-callability, and the router's existing redirect check) exactly as designed, rather than inventing a parallel "go to onboarding" path. It also means a future feature that adds more tables (Occasions, Budgets, Savings, etc.) only needs to add its own table(s) to `deleteAllUserData()`'s wipe list — the onboarding-reset behavior requires no change at all.

**Alternatives considered**: A dedicated `resetApp()` method that force-navigates without going through the existing onboarding-gate logic — rejected as a parallel, redundant path to a decision `ResolveOnboardingStatus` already makes correctly; two places deciding "should onboarding show" is exactly the kind of duplicated-logic risk the constitution's Refactoring Discipline warns against. Requiring the user to manually restart the app after deletion — rejected as materially worse UX than a same-session graceful reset, and not actually simpler to implement.

## 7. Charts without a new dependency

**Decision**: The monthly trend and category breakdown are rendered with simple, hand-built Flutter widgets (`CustomPainter` for the trend line/bars, and a `Row`/`Column`-based proportional-bar layout for the category breakdown — closely following the same visual language 007's own `CategoryBreakdownBar` widget already establishes) rather than adding a charting package.

**Rationale**: Both charts this feature needs are simple (a handful of monthly bars/points; a handful of proportional category bars) — well within what `CustomPainter` and basic layout widgets can express cleanly, and avoids a second new dependency beyond `share_plus` for a capability this app will only need lightly at this stage (constitution: "avoid unjustified new dependencies," and "prefer the simplest architecture that can scale" — nothing about this feature's charts needs a general-purpose charting library's full feature set). This keeps the RTL-mirroring requirement (FR-006) fully under this codebase's own control rather than depending on a third-party package's own (unverified) RTL support.

**Alternatives considered**: Adding `fl_chart` or a similar charting package — rejected for now as more capability than two simple charts justify; revisit if a future feature (e.g., Budgets' progress bars, already flagged in ROADMAP-PLAN.md §9 as a likely shared-component candidate) needs materially more charting sophistication, at which point promoting to a real charting dependency would be justified by two features needing it, not one.

## 8. Delete confirmation UX (FR-014/FR-015, SC-004)

**Decision**: Tapping "Delete My Data" in `SettingsPage`'s new Danger Zone section navigates to a dedicated `DeleteDataConfirmationPage` (not an in-place dialog, given the severity) that (1) displays an explicit, unambiguous permanent/irreversible warning, (2) requires the user to type an exact localized confirmation phrase into a text field before the destructive button enables at all, and (3) only then lets them tap the now-enabled "Delete Everything" button — two distinct, deliberate actions (typing the phrase, then tapping), satisfying SC-004's "no fewer than 2 distinct deliberate confirmation actions" and the constitution's Financial Domain Override call for a "strong, explicit, typed-confirmation dialog."

**Rationale**: A dedicated full-screen destination (rather than a modal dialog) gives this the visual weight its severity warrants and leaves room for the full warning copy without cramming it into a dialog; the typed-phrase gate is a well-established pattern (used by many products for exactly this "point of no return" moment) that is meaningfully harder to trigger by accident than any single tap or even a two-tap "are you sure?" dialog, which users learn to dismiss reflexively.

**Alternatives considered**: A simple two-button `AppConfirmDialog` ("Cancel"/"Delete") — rejected as insufficiently deliberate for the single most destructive action in the app; the existing `AppConfirmDialog` pattern is reused throughout the app for reversible-enough actions (archiving, single-record deletion with undo), and re-using it unmodified here would under-signal the irreversibility difference. Biometric/PIN re-authentication before deletion — rejected as out of scope: the app has no authentication system yet (App Lock is a V3 roadmap item, ROADMAP-PLAN.md §V3.1, explicitly deferred), so requiring it here would introduce a capability class this feature has no business introducing on its own.

## 9. Navigation placement

**Decision**: `ReportsPage` is nested under the existing People `StatefulShellBranch` as `/finance/reports`, alongside 007's own `/finance`, `/finance/entries/new`, `/finance/categories` routes (same branch, same precedent, 007 research.md Decision 9). `DataExportPage` and `DeleteDataConfirmationPage` are nested under the existing Settings branch as `/settings/export` and `/settings/delete-data`. `ReportsPage`'s app bar carries one convenience action-icon linking to `/settings/export`, so a user already looking at their data can reach export within the 3-tap ceiling (SC-002) without needing to already know it lives in Settings.

**Rationale**: Keeps every new route inside the two branches ROADMAP-PLAN.md's own Navigation Plan (§8) already designated for exactly this kind of nested, non-tab-worthy screen — no new bottom-nav tab is remotely justified for either half of this feature. The Reports-to-Export shortcut is a small, low-risk UX addition that directly serves SC-002 without duplicating any navigation logic (it is one more `GoRoute` push, nothing new architecturally).

**Alternatives considered**: A dedicated "Reports" or "Privacy" bottom-nav tab — rejected outright per ROADMAP-PLAN.md §8's explicit guidance that Occasions is the earliest point a 4th tab becomes even plausible, and neither Reports nor privacy controls are remotely in that category of primary-pillar frequency.

## 10. Testing approach specifics

**Decision**: Same three-tier approach as every prior feature — but `DeleteAllUserData`/`data_wipe.dart` additionally gets a dedicated test against a real in-memory `drift` database (`NativeDatabase.memory()`) that forces a failure partway through the transaction (e.g., a faked constraint violation on one table) and asserts every other table is provably still fully intact afterward — a mocked-repository-only test cannot actually prove SQL-level transactional atomicity, so this one test intentionally exercises the real `drift` transaction mechanism rather than a fake.

**Rationale**: FR-018/SC-005 are this feature's highest-stakes requirement (constitution Financial Domain Override); a test that only asserts "the mock's delete methods were called" would not actually verify atomicity, which is a property of the real SQL transaction boundary, not of the Dart call sequence around it.

**Alternatives considered**: None — this is the direct, necessary consequence of what FR-018 actually requires being verified, not an open design question.
