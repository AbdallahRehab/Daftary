# Phase 0 Research: OCR Paper-to-Transaction Entry

All Technical Context unknowns from `plan.md` are resolved below. The spec (009) carries zero `NEEDS CLARIFICATION` markers. This document resolves the remaining technical/design decisions, reusing precedents from 001/008 wherever they apply (constitution Refactoring Discipline).

## 1. OCR engine choice — and an honest Arabic-accuracy trade-off

**Decision**: `google_mlkit_text_recognition` (the Flutter plugin for Google ML Kit's on-device Text Recognition v2, Latin script model), used identically on Android and iOS.

**Rationale**: Fully on-device (no network call, satisfying FR-019/Principle XII), free, mature/actively maintained Flutter plugin, good accuracy on printed Latin text and digits (both Western and — empirically, since it recognizes character glyphs rather than semantically parsing numerals — often usable on Arabic-Indic digit glyphs too, verified during implementation with real fixture images per research Decision 6/testability). This directly matches the product brief's own request (docs/project.txt §19) to evaluate ML Kit against alternatives and recommend one.

**The honest limitation this spec is built around**: Google ML Kit's on-device Text Recognition v2 ships script-specific bundled models for Latin, Chinese, Devanagari, Japanese, and Korean — it has **no dedicated Arabic-script model**, on either Android or iOS (the iOS build of this plugin also uses Google's own on-device models, not Apple's Vision framework, so it inherits the same gap). Apple's own Vision framework (`VNRecognizeTextRequest`) does support Arabic as a recognition language on modern iOS versions, but adopting it would mean building and maintaining two structurally different native OCR integrations (Vision on iOS, ML Kit on Android) for one feature, a materially larger implementation/maintenance cost for a v1.5 feature. **This is why the spec's own Assumptions section explicitly documents "handwriting is best-effort, not guaranteed" and, more specifically here, why printed Arabic name text will recognize measurably worse than printed English name text or digits in v1.5** — and exactly why the mandatory review/confirm gate (User Story 2) and the confidence/inferred visual distinction (User Story 3) are load-bearing product requirements, not nice-to-haves: the product must remain fully safe and useful even when this specific, named limitation is in play.

**Alternatives considered**: Apple Vision on iOS + ML Kit on Android (better Arabic support on iOS only) — rejected for v1.5 as disproportionate integration complexity (two native pipelines behind one interface) for a partial, platform-inconsistent improvement; noted as a good candidate for a later, dedicated OCR-quality iteration. Tesseract OCR with bundled Arabic `traineddata` (fully open-source, on-device, genuine Arabic support) — rejected for v1.5: meaningfully larger app bundle size (`traineddata` files run tens of MB per language), slower inference on mid-range Android than ML Kit's optimized native models, and materially worse out-of-the-box accuracy than commercial engines even for Arabic without significant tuning — a worse cost/accuracy trade-off than accepting the documented Latin-only limitation. Any cloud OCR/Vision API (Google Cloud Vision, Azure, etc.) — rejected for v1.5 per FR-019/the spec's Assumptions: this feature is scoped as fully on-device/offline/no-consent-flow-required; a future, separately consent-gated cloud-assisted mode is left as a named future enhancement, not built now.

## 2. Crop/rotate/enhance pipeline

**Decision**: `image_cropper` (native crop/rotate UI plugin, Android + iOS) for the interactive crop/rotate step (FR-002), followed by a small deterministic enhancement pass using the pure-Dart `image` package (brightness/contrast normalization via a simple linear stretch — no ML-based "smart" enhancement).

**Rationale**: `image_cropper` provides a polished, native, well-tested crop/rotate UX with zero custom gesture-handling code to build/maintain. The enhancement step is deliberately simple and deterministic (a documented, explainable transform) rather than an ML-based auto-enhance, keeping the whole pre-OCR pipeline fast, predictable, and easy to unit-test with fixture images, consistent with the constitution's "prefer the simplest architecture that can scale" guidance and Principle VIII's general preference for determinism in this codebase's calculation-adjacent code.

**Alternatives considered**: A fully custom crop/rotate UI built on `CustomPaint`/gesture detectors — rejected as substantial, unjustified UI engineering effort duplicating what a maintained plugin already does well (constitution: "is there a simpler solution?"). An ML-based auto-enhance (e.g. a bundled super-resolution/denoising model) — rejected as disproportionate complexity/size for v1.5 given OCR accuracy is already bounded by Decision 1's engine choice, not by image quality alone.

## 3. Candidate-entry parsing (deterministic, non-AI)

**Decision**: A pure-Dart, unit-testable `CandidateEntryParser` that: (a) splits recognized text into lines (using the OCR engine's own line/block segmentation, not just raw newline splitting); (b) for each line, extracts the first/last numeric token as the amount candidate, reusing the existing `core/money/numeral_parser.dart` for Arabic-Indic/Western digit normalization; (c) treats the remaining non-numeric text on the line as the name candidate; (d) separately scans the whole recognized-text block (not per-line) for a date-shaped token (common DD/MM/YYYY-style patterns) and an occasion-heading-shaped line (a line containing a recognized occasion-type keyword or positioned as a title/first line) to pre-fill date/occasion for the whole batch; (e) marks every field as either `confidence: <engine score>` (Decision 4) or `inferred: true` depending on whether it was a direct per-token OCR read or a derived/defaulted guess.

**Rationale**: This is exactly the deterministic, explainable parsing constitution Principle VIII and the spec's own Assumptions call for ("structuring is done by deterministic text-pattern parsing... not an LLM") — every candidate field's provenance (read vs. inferred) is a simple, traceable fact the parser itself records, which is what powers User Story 3's confidence/inferred UI distinction without inventing a second, opaque scoring system.

**Alternatives considered**: An on-device or cloud LLM performing the structuring step (as the product brief's own §3 step "AI understands the structure" suggests as one possible framing) — explicitly rejected for this v1.5 spec per the Assumptions section and constitution Principle IX; the product's roadmap places any LLM-assisted extraction in a later, clearly-scoped AI tier, not here. A rigid single-format parser (e.g., assuming every line is exactly "Name — Amount") — rejected as too brittle for real handwritten/printed Egyptian paper lists, which vary in separator character, spacing, and whether the amount leads or trails the name; the token-based approach (numeric token extraction, remainder as name) is materially more robust and still fully deterministic.

## 4. Confidence signal availability

**Decision**: Where `google_mlkit_text_recognition`'s result objects expose a usable per-element signal (in the current plugin API, elements do not carry a fine-grained numeric confidence score the way some cloud OCR APIs do), the app maps it to a coarse three-level indicator (`low`/`medium`/`high`) rather than displaying a fabricated precise percentage; every field the parser derived rather than read directly from a token (direction defaults, defaulted dates, occasion guesses) is always shown as `inferred`, never assigned a confidence level at all — this distinction is structural in `FieldConfidence` (data-model.md), not a UI-only labeling choice.

**Rationale**: Directly implements FR-013's careful wording ("where the underlying text-recognition step provides a confidence score") and avoids the specific failure mode the spec calls out by name — "never presenting an inferred value with the same visual trust signal as a genuinely high-confidence OCR read." Being honest about what is actually measured (a coarse signal, not a precise percentage) avoids over-promising accuracy the underlying engine does not actually provide.

**Alternatives considered**: Synthesizing a fake numeric confidence (e.g., from text region size or contrast) to make the UI look more sophisticated — rejected as actively misleading, contrary to the constitution's "AI responses/derived signals are never blindly trusted" spirit and to the spec's own explicit anti-goal.

## 5. `MoneyTransaction`/`Occasion` extension vs. a parallel record

**Decision**: Exactly the same call as 008's Decision 1: a confirmed `CandidateEntry` becomes an ordinary `MoneyTransaction` row (or, when tagged to an occasion, an `occasionContribution`-kind row exactly per 008), gaining two new columns (`source` enum `manual`/`ocr`, default `manual`; `ocr_scan_id` nullable FK) rather than a second, parallel "OCR transaction" table.

**Rationale**: Identical reasoning to 008 Decision 1 — a single balance/history/audit mechanism, no risk of an OCR-confirmed entry disagreeing with what the person's profile or an occasion's totals show. This is also what makes FR-007/Principle X structurally enforceable: there is exactly one method (`ConfirmScanBatch`, delegating to `TransactionsRepository`/`OccasionsRepository`'s existing write methods) that can ever turn scan data into ledger data.

**Alternatives considered**: A separate `OcrTransactions` table reconciled at query time — rejected per 008's identical precedent (duplicated/divergence-prone balance logic).

## 6. Testing the OCR/crop pipeline without a real device/model

**Decision**: `TextRecognitionService` and `ImagePreparationService` are Domain-facing interfaces (research.md/plan.md Structure Decision); their real implementations wrap the plugins, but all use case/Cubit/parser tests run against fakes. The `CandidateEntryParser` itself takes recognized-text-with-positions as plain Dart input (no plugin type in its signature), so it is tested with a large fixture table of real-world-shaped strings (clean, noisy/misread characters, mixed Arabic/English, mixed numeral systems, subtotal/header lines) with zero device or ML model dependency, independent of Decision 1's engine choice.

**Rationale**: Directly satisfies constitution Principle XVI (Testability by Design) and keeps the parser's correctness verifiable in CI without a physical device or an ML Kit runtime, which is not available in a typical headless test environment.

**Alternatives considered**: Testing the parser only via `integration_test` against real captured images — rejected as insufficient coverage (slow, flaky, requires a device, cannot enumerate edge cases like OCR character-confusion patterns deterministically) as the *only* test strategy; `integration_test` is still included for true end-to-end confidence, but unit tests carry the correctness burden.
