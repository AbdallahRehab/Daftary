# Feature Specification: Multi-Currency Support

**Feature Branch**: `018-multi-currency-support`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "Roadmap V3.4 — Multi-Currency Support. The app's core/money/Money type is currently implicit-EGP-only, reused by every feature (001 Transactions, 007 Income/Expense, 008 Occasions, 010 Budgets, 011 Savings Goals). Add an explicit ISO 4217 currency code alongside every stored monetary amount across all of them, a 'primary currency' app-level setting (default EGP) used for every aggregated total, and manual/static exchange rates the user enters and maintains themselves in Settings — explicitly NOT a live rate-fetching backend/API (that would be this app's second-ever network dependency after AI Assistant, and is out of scope). 'No network call is introduced by this feature' is a hard, testable requirement. Existing pre-feature records are migrated to explicit EGP, never left ambiguous. An amount not in the primary currency is converted only for aggregation/summary display using the user's manual rate; its own original currency/amount is always preserved on the record itself. A currency with no rate entered blocks aggregation into a total with a clear message, never silently treated as 1:1 or omitted. This is the most cross-cutting V3 feature specified this session — no dependency on 015/016/017, but touches shared core/money code and every existing feature's data layer."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Record an Amount in a Non-Primary Currency (Priority: P1)

A user who occasionally deals in a currency other than their primary one (e.g. a friend paid them in USD, or they track a foreign-currency expense) wants to record that transaction, income/expense entry, occasion contribution, budget line, or savings contribution in the currency it actually happened in, rather than being forced to mentally convert it to EGP first.

**Why this priority**: This is the entire point of the feature — without the ability to actually record a non-primary-currency amount, nothing else here has value, and the app remains exactly as EGP-only as it is today.

**Independent Test**: Can be fully tested by creating a new transaction (or entry/contribution/budget line/savings contribution) with a currency other than the primary currency, confirming it saves with that currency and its original entered amount, and confirming it displays with that currency's indicator wherever it appears afterward.

**Acceptance Scenarios**:

1. **Given** the user's primary currency is EGP, **When** they record a new Person transaction (001) and select USD with an amount of 100, **Then** the transaction is saved as exactly 100 USD — never silently converted to or stored as an EGP amount.
2. **Given** the same setup, **When** they view that transaction later in the person's history, **Then** it displays as "100 USD," not "100 EGP" and not a converted EGP figure standing in for the original.
3. **Given** the user is recording any new amount-bearing record in any feature (Income/Expense entry (007), Occasion contribution (008), Budget planned/actual line (010), Savings Goal target or contribution (011)), **When** they open the amount entry field, **Then** a currency selector is present, defaulting to the app's current primary currency, changeable to any currency the user has configured (Assumptions).
4. **Given** the user picks a currency other than the primary one for a new record, **When** they save it, **Then** both the amount and the chosen currency are stored together as one inseparable fact about that record.
5. **Given** the user never touches this feature at all, **When** they use the app exactly as before, **Then** every amount they enter defaults to and is recorded in EGP with zero additional steps or prompts — this feature changes nothing about the existing single-currency experience until actively used.

---

### User Story 2 - See Aggregated Totals Correctly Across Currencies (Priority: P1)

A user with amounts recorded in more than one currency wants every existing aggregated total in the app (a person's net balance, the Overview's totals, the Finance summary, a Budget's planned/actual/remaining, the Savings overview's combined total) to still show one single, meaningful number — converted to their primary currency using a rate they themselves control — rather than either crashing, silently adding incompatible currencies together, or hiding the non-primary-currency amounts from the total entirely.

**Why this priority**: Without correct aggregation, adding a second currency to any single record would break every existing summary screen in the app — this is what makes the feature safe to use at all beyond a single isolated record, and is equally foundational as User Story 1.

**Independent Test**: Can be fully tested by recording amounts in two different currencies against the same aggregate (e.g. two transactions with the same person, one EGP one USD), setting a manual exchange rate for the non-primary currency, and confirming the aggregate total correctly reflects the converted sum while each underlying record still shows its own original currency/amount.

**Acceptance Scenarios**:

1. **Given** a person has one transaction of 1,000 EGP and one of 100 USD, and the user has set an exchange rate of 1 USD = 48.50 EGP, **When** the user views that person's net balance, **Then** the balance is computed and shown in the primary currency (EGP), correctly incorporating the USD transaction's converted value (100 × 48.50 = 4,850 EGP-equivalent), while the transaction history still lists the original 100 USD transaction as "100 USD," never silently rewritten to an EGP figure.
2. **Given** the same setup, **When** the user views the person's transaction history, **Then** each individual transaction shows its own original currency and amount, unconverted, alongside (not instead of) any converted-total context shown at the aggregate level.
3. **Given** the user has entries in a currency for which no exchange rate has been configured, **When** they view any total that would need to include that currency's amounts, **Then** the system clearly indicates that total is incomplete/blocked pending a rate for that currency, rather than silently treating the missing rate as 1:1, silently omitting those amounts from the sum, or crashing.
4. **Given** the user then sets a rate for the previously-missing currency, **When** they return to that total, **Then** it now correctly includes the previously-blocked amounts.
5. **Given** the Overview totals (001), Finance summary (007), a Budget's totals (010), and the Savings overview's combined total (011) all potentially span multiple currencies, **When** the user views each, **Then** every one of them independently applies the same conversion/blocking rules consistently — no aggregate screen in the app is exempt from this feature's rules.

---

### User Story 3 - Set the Primary Currency and Manage Exchange Rates (Priority: P1)

A user wants to choose which currency their totals are shown in, and wants to keep their own manually-entered exchange rates up to date as real-world rates change, entirely under their own control with no network dependency.

**Why this priority**: Without a way to configure the primary currency and maintain rates, User Story 2's aggregation has nothing to work from — this is the necessary control surface for the other two P1 stories, hence equally P1.

**Independent Test**: Can be fully tested by opening currency settings, changing the primary currency, adding/editing an exchange rate for a second currency, and confirming both changes are reflected immediately in subsequent aggregate calculations.

**Acceptance Scenarios**:

1. **Given** the user opens Settings, **When** they navigate to currency settings, **Then** they see the current primary currency (EGP by default) and a management view for exchange rates against it.
2. **Given** the user changes the primary currency to a different one (e.g. USD), **When** they confirm, **Then** every future aggregate calculation uses the new primary currency, and existing records retain their own original currency/amount unchanged — only the currency totals are computed in is affected, never any individual record's stored data.
3. **Given** the user adds an exchange rate for a new currency (e.g. "1 USD = 48.50 EGP" when EGP is primary), **When** they save it, **Then** the rate, together with the moment it was entered/last updated, is stored and immediately available for aggregation.
4. **Given** the user edits an existing exchange rate to reflect a more current real-world value, **When** they save the change, **Then** all subsequent aggregate calculations use the new rate; the "last updated" timestamp shown alongside the rate updates to reflect when the user actually made this change.
5. **Given** the user attempts to enter a zero or negative exchange rate, **When** they submit, **Then** the system rejects it with a clear explanation, since a rate must be a positive number.
6. **Given** the user views the exchange-rate management screen, **When** it renders, **Then** it clearly communicates that rates are entered and maintained manually by the user, are not fetched automatically from any external source, and may become outdated if not kept current — setting an honest expectation rather than implying live/automatic rates.
7. **Given** the user changes the primary currency to a currency that itself has no configured rate relative to the previous primary currency, **When** they confirm the change, **Then** the system requires a rate to be set for the previous primary currency (now a "foreign" currency relative to the new primary) before or immediately after the switch, since totals blending the two currencies would otherwise become incomplete/blocked (User Story 2 Scenario 3) the moment the switch takes effect.

### Edge Cases

- What happens to every amount recorded before this feature existed? Every pre-existing record across every feature (001/007/008/010/011) is migrated to carry an explicit EGP currency code — never left with an ambiguous or null currency — since EGP was always the implicit currency of every record recorded before this feature shipped.
- What happens when a user has exactly one currency in use (the common case, at least initially) and never sets any exchange rate? All totals compute normally with zero conversion needed, since there is nothing to convert — the feature is fully invisible in its effect on a single-currency user beyond the presence of a (default, unused) currency indicator.
- What happens when a currency's exchange rate is deleted/removed after having been set? Any total that would need to include that currency's amounts reverts to the same "blocked, needs a rate" state as if the rate had never been set (User Story 2 Scenario 3) — the underlying records themselves are never altered or lost.
- What happens with a deterministic calculator that depends on a single consistent currency, such as Savings Goals' (011) what-if projection calculator? Its inputs/outputs are computed and expressed in the currency of the specific goal being projected (a goal has one target currency, set at creation, consistent with how the goal's own target/contributions already share one currency per goal — see Key Entities) — never silently blended across currencies within a single goal's own calculation.
- What happens when the user records a transaction/entry/contribution in a currency, then later changes the primary currency, then views a total that includes that record? The record's own stored currency/amount never changes; only the conversion applied at aggregation time changes, using whatever rate is configured between that record's currency and the (now different) primary currency.
- What happens when rounding is needed during a currency conversion for a total? The conversion result is rounded to the target currency's standard smallest unit (matching this app's existing "integer minor units, never floating point" money-handling convention) using a single documented, deterministic rounding rule — never an ad hoc or inconsistent rounding choice across different screens.
- What happens if the app's language or theme changes while a currency picker, the exchange-rate management screen, or a "rate needed" blocked-total message is visible? All remain correctly laid out, fully legible, and fully localized in RTL/LTR and both themes with no truncation, including currency codes/symbols that must read correctly in both directions.
- What happens to a currency that was used on at least one existing record but is later removed from the user's configured currency list (if such removal is offered)? The existing records retain their original currency (never silently reassigned), and that currency's exchange rate (if previously set) remains available for aggregation purposes even though it's no longer offered as a *new*-record selection — mirroring how this app already treats an archived Category (007) continuing to display correctly on past entries while being excluded from new-entry pickers.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST store an explicit currency code alongside every monetary amount recorded by every existing amount-bearing entity: Person transactions (001), Income/Expense entries (007), Occasion contributions (008), Budget planned and actual amounts (010), and Savings Goal target amounts and Savings Contributions (011).
- **FR-002**: The system MUST migrate every record that existed before this feature shipped to carry an explicit EGP currency code, with zero records left in an ambiguous, null, or unset currency state after migration.
- **FR-003**: The system MUST provide a currency selector on every amount-entry form across every feature listed in FR-001, defaulting to the app's currently configured primary currency, and allowing the user to choose any other currency they have configured (Assumptions).
- **FR-004**: The system MUST store the currency chosen at the time a record is created as a permanent, inseparable attribute of that record's amount — never silently converted, overwritten, or reassigned to a different currency by any later action other than the user directly editing that specific record.
- **FR-005**: The system MUST provide an app-level "primary currency" setting, defaulting to EGP, changeable by the user in Settings; changing it MUST affect only the currency in which future aggregate totals are computed and displayed, and MUST NOT alter any existing record's own stored currency or amount.
- **FR-006**: The system MUST allow the user to manually enter, view, and edit an exchange rate between the primary currency and each other currency in use, expressed as "1 unit of [foreign currency] = [X] units of [primary currency]," and MUST reject a zero or negative rate with a clear explanation.
- **FR-007**: The system MUST display, alongside every manually-entered exchange rate, the date/time it was last set or updated, and MUST clearly and persistently communicate (not a one-time dismissible notice) that rates are manually maintained by the user and not automatically fetched or kept current by the system.
- **FR-008**: For every aggregated/summed total in the app that could include amounts in more than one currency — including at minimum a Person's net balance and transaction totals (001), the Overview's totals (001), the Finance summary and category breakdown (007), Occasion contribution totals (008), a Budget's per-category and aggregate planned/actual/remaining (010), and the Savings overview's combined currently-saved total (011) — the system MUST convert every non-primary-currency amount to the primary currency using the user's configured exchange rate before summing, and MUST display the result labeled with the primary currency.
- **FR-009**: When an aggregate total (FR-008) would need to include an amount in a currency for which no exchange rate is currently configured, the system MUST NOT silently omit that amount, silently treat the missing rate as 1:1, or crash — it MUST instead clearly indicate to the user that this total is incomplete/blocked pending a rate for that specific currency, and MUST offer a direct path to set one.
- **FR-010**: Every screen that displays an individual amount-bearing record (not an aggregate total) MUST always show that record's own original currency and original amount, unconverted — a converted-to-primary-currency figure MAY be shown additionally at an aggregate/summary level, but MUST NEVER replace or hide a record's own original currency/amount on the record itself.
- **FR-011**: The system MUST compute Savings Goals' (011) deterministic what-if projection calculator (and any other single-entity deterministic calculator in the app that depends on internal amount consistency) entirely within that specific entity's own currency, since a goal has exactly one currency for its target and all its contributions (see Key Entities) — the calculator MUST NEVER blend currencies within one entity's own calculation.
- **FR-012**: The system MUST require a valid exchange rate to exist between the previous and new primary currency at the moment the user changes the primary currency setting, if any existing record anywhere in the app is denominated in the previous primary currency — prompting the user to set that rate as part of completing the currency switch, so no total becomes silently blocked immediately after the switch without the user having been told why.
- **FR-013**: The system MUST round every currency-conversion result, for display and aggregation purposes, to the target currency's standard smallest unit, using one single documented, deterministic rounding rule applied consistently everywhere a conversion occurs in the app — never floating-point arithmetic, and never an inconsistent rounding rule between different screens (constitution Principle VIII).
- **FR-014**: This feature MUST NOT introduce any network call anywhere in the app — every exchange rate is entered and stored entirely locally by the user, with zero automatic fetching from any external rate source; this MUST remain independently and continuously true regardless of whether any other network-capable feature (e.g. a future AI Assistant) exists in the same build.
- **FR-015**: A user who never actively changes the primary currency away from EGP and never records an amount in a non-EGP currency MUST experience the app exactly as it behaves today — zero additional prompts, zero behavior change, zero visible complexity beyond an unobtrusive currency indicator now present alongside amounts.
- **FR-016**: The system MUST present every new or changed screen introduced by this feature (currency selector, exchange-rate management screen, primary-currency setting, "rate needed" blocked-total messaging, and every existing amount display now also showing a currency indicator) fully localized in Arabic and English, with correct RTL/LTR layout for currency codes/symbols and amounts, and correctly themed in both light and dark mode.
- **FR-017**: The system MUST NOT alter, migrate, or affect any existing People, Transaction, Income/Expense, Occasion, Budget, or Savings Goal calculation logic beyond the currency dimension itself and the migration described in FR-002 — the underlying business rules (balance derivation, budget percentage-used, savings progress, etc.) established by each of those features' own specs remain unchanged, now simply operating on currency-aware amounts instead of implicitly-EGP amounts.

### Key Entities *(include if feature involves data)*

- **Currency**: A supported ISO 4217 currency (code, e.g. `EGP`/`USD`/`EUR`/`SAR`/`AED`, plus a display symbol/name). The app ships with a sensible starter set of commonly relevant currencies (Assumptions) and EGP is always present and cannot be removed, since it is the app's original and default currency.
- **Primary Currency Setting**: A single, app-level configuration value naming which `Currency` every aggregate total is computed and displayed in. Defaults to EGP. Changing it affects only future aggregation/display, never any existing record's own stored currency/amount (FR-005).
- **Exchange Rate**: A user-maintained, manually-entered rate between one non-primary `Currency` and the current `Primary Currency Setting`, expressed as "1 unit of [currency] = [X] units of primary currency." Attributes: the rate value (a positive number), the currency it applies to, and a last-updated timestamp. Never fetched automatically; a currency with no `Exchange Rate` configured cannot be included in any aggregate total (FR-009).
- **Currency-Aware Amount** *(a shared attribute pattern applied to every existing amount-bearing entity, not a new standalone entity)*: Every existing amount field across `MoneyTransaction` (001), `FinanceEntry` (007), an Occasion contribution (008), a `Budget`'s planned/actual amounts (010), and `SavingsGoal`/`SavingsContribution` (011) gains a paired `Currency` alongside its existing integer-minor-units amount — the amount and its currency are always read, written, and displayed together as one inseparable fact, never one without the other.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can record a new amount in a non-primary currency, in any feature listed in FR-001, in the same amount of time and number of steps as recording one in the primary currency plus exactly one additional currency-selection tap.
- **SC-002**: For any test scenario combining at least 3 currencies across at least 20 records feeding into a single aggregate total, the computed total exactly matches the sum of each record's amount independently converted to the primary currency at its configured rate, with zero discrepancies and zero silently-dropped records.
- **SC-003**: 100% of individual-record displays (never aggregate totals) show that record's own original currency and amount unconverted, verified across every screen listed in FR-001/FR-008, with zero exceptions found in a full screen-by-screen audit.
- **SC-004**: A user attempting to view a total that includes a currency with no configured rate is shown a clear, actionable "rate needed" state 100% of the time — verified with zero instances of a silently-1:1-treated or silently-omitted amount across at least 10 varied missing-rate test scenarios.
- **SC-005**: A user can migrate an existing installation (with pre-feature EGP-only data) to this feature's first launch and find every single pre-existing record correctly and explicitly labeled EGP, with zero records showing an ambiguous or missing currency, across a migration test covering at least 100 pre-existing records spanning all five affected features.
- **SC-006**: Zero network requests are observed anywhere in the app as a direct result of any action within this feature (adding/editing a currency, setting an exchange rate, changing the primary currency, viewing any converted total) across a full manual test pass with connectivity fully disabled.
- **SC-007**: Switching the app language between Arabic and English, or switching between light and dark mode, produces zero layout, alignment, or truncation defects on the currency selector, the exchange-rate management screen, the primary-currency setting, or any "rate needed" messaging.
- **SC-008**: A user who never interacts with this feature and never enters a non-EGP amount observes byte-for-byte identical totals and behavior to the app's pre-feature EGP-only experience, verified by a full regression pass across People/Transactions/007/008/010/011 with zero behavioral differences found.

## Assumptions

- **Manual/static exchange rates only — no live rate-fetching**: Per this task's explicit instruction and ROADMAP-PLAN.md §V3.4's own framing, a live rate-fetching integration would be this app's second-ever network dependency (after a future AI Assistant, spec 014) and is a materially bigger, separate architectural decision deliberately deferred out of this spec's scope. This feature's exchange rates are entirely user-entered and user-maintained, with an explicit, persistent "not automatically kept current" disclosure (FR-007) so the user's expectations are set honestly rather than implying a live-rate experience this feature does not provide.
- **Starter currency set**: The app ships with a small, sensible starter list of currencies beyond EGP (e.g. USD, EUR, SAR, AED, GBP — commonly relevant to an Egyptian user's likely cross-border money relationships) available in every currency picker without any setup, while EGP remains permanently present and non-removable as the app's original default. The exact starter list is a content/configuration decision refinable at implementation time, not an architecturally binding requirement of this spec. A user is not assumed to be able to add an arbitrary custom ISO 4217 code beyond this starter set in this spec's scope — that is a reasonable, low-risk future extension if requested, not assumed here.
- **One currency per entity for entities with internal consistency needs**: A `SavingsGoal` (011), a `Budget` (010) category line, and similar single-entity, internally-aggregating records are assumed to carry one currency for their own target/planned figures, consistent with how each such entity already represents one coherent plan — the feature does not attempt to let a single goal's target be in one currency while its contributions are recorded in several different currencies and silently reconciled; a contribution recorded in a different currency than its goal's own currency is converted to the goal's currency at the configured rate at the moment it's logged, and the goal's own progress/projection math (FR-011) then operates on that one consistent currency throughout, exactly as it does today.
- **Rounding rule**: Currency-conversion results round to the nearest smallest unit of the target currency using standard "round half up" rounding, applied identically everywhere a conversion occurs — chosen as the most broadly understood, predictable convention, consistent with the constitution's "one single documented, deterministic rounding rule" requirement (FR-013) and this app's existing "no floating point" money-handling discipline (`core/money`).
- **Implementation-order note (this spec's own distinguishing characteristic)**: Unlike 015/016/017 (each a purely additive new feature module), this spec's changes are the most cross-cutting of any V3 item specified this session — every one of 001/007/008/010/011's existing data/domain layers requires a currency-column migration to its underlying storage, and `core/money`'s currently-implicit-EGP `Money` type itself needs to become currency-aware. If this feature is implemented after some or all of 001/007/008/010/011 already exist in code (as the broader roadmap sequencing implies), its own `/speckit-plan` must treat each affected feature's migration as a first-class, individually-tested step — never a single undifferentiated "add currency everywhere" change — precisely because a mistake in any one of these five migrations risks silently corrupting that feature's existing balance/total calculations, which the constitution's Financial Domain Override treats as the least acceptable class of defect in this app.
- **Currency symbol/formatting**: Reuses and extends the app's existing locale-aware number-formatting approach (`core/money`) rather than inventing a second formatting mechanism — a currency code/symbol is added alongside the existing formatted amount, following the same RTL/LTR-correct placement conventions already required by constitution Principle XIII for the app's current EGP-only formatting.
- **Navigation placement**: Primary-currency setting and exchange-rate management are reached from Settings, alongside Language/Theme/Security (015)/Notifications (017) — exact placement is a navigation/IA decision made at planning time, not a behavioral requirement of this spec.
